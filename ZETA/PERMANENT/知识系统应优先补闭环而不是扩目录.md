# 知识系统应优先补闭环而不是扩目录

## 一句话判断

当知识库已经有稳定入口、目录、标签、模板和维护清单时，继续新增目录的收益会快速下降；更应该补齐输出、复习、验证、决策回溯、恢复与隐私这些闭环。

## 解决的问题

这个判断用来阻止“越整理越复杂”。如果每次遇到新问题都新增文件夹、标签或仪表盘，系统会变得更难用；如果补的是闭环，旧内容会更容易回到项目、成果和长期判断。

## 依据

- [[00-管理/知识库优化路线图]] 已明确不建议继续新增很多文件夹。
- [[00-管理/审查记录/2026-05-10-模块健康检查]] 的结论是继续稳定 `HUB / PARA / ZETA / DAILY / SYSTEM`，不新增一级目录。
- [[00-管理/审查记录/2026-05-12-闭环增强记录]] 把新增能力限制在现有入口内。
- [[00-管理/审查记录/2026-05-12-决策-补闭环而不是扩目录]] 记录了当时的选项、代价和复查条件。
- [[HUB/Outputs]] 和 [[HUB/Review]] 分别处理成果出口和高价值复习，不承担长期正文保存。

## 边界

如果出现全新的长期责任区、独立资料类型或现有入口无法解释的工作流，可以考虑新增结构。但新增前要先确认：

- 是否能通过现有 MOC、索引或链接解决。
- 是否只是一个短期项目或临时资料。
- 是否会带来新的维护成本。
- 是否已经有 3 篇以上相关笔记需要长期组织。

## 复用场景

- 想新增一级目录时，先检查是否只是缺少 [[HUB/Outputs]]、[[HUB/Review]] 或 [[HUB/Tasks]] 的动作。
- 想新增标签时，先判断能否用链接或 MOC 表达关系。
- 想引入新插件时，先检查 [[SYSTEM/必要插件清单]] 是否已有能力覆盖。
- 想批量移动正文时，先确认入口、索引和反向链接是否真的失效。

## 下次行动

遇到“要不要新增结构”的问题时，先写一条决策记录，使用 [[Templates/原生模板/决策记录模板]]，再决定是否改动目录或标签体系。
