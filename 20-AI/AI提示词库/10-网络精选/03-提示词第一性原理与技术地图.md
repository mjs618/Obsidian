# 提示词第一性原理与技术地图

## 第一性原理

提示词不是“咒语”，而是给模型构造任务环境。一个稳定的提示词通常同时解决 6 件事：

1. **目标**：要模型产出什么结果。
2. **上下文**：模型需要知道哪些背景。
3. **角色**：用什么专业视角处理任务。
4. **过程**：应该按什么步骤思考或执行。
5. **格式**：结果应该如何组织。
6. **验收标准**：怎样判断输出是否合格。

如果一个提示词效果差，通常不是因为“词不够神”，而是这 6 个要素里有缺口。

## 技术地图

| 技术 | 适合什么时候用 | 核心做法 | 风险 |
| --- | --- | --- | --- |
| Zero-shot | 任务简单、输出标准明确 | 直接给目标和格式 | 容易受歧义影响。 |
| Few-shot | 需要稳定风格或分类标准 | 给 2-5 组输入/输出例子 | 示例质量差会污染输出。 |
| Role prompting | 需要专业视角 | 指定身份、经验、判断标准 | 只写角色不写任务，效果有限。 |
| Contextual prompting | 有背景依赖 | 提供业务背景、限制和目标用户 | 上下文太长会稀释重点。 |
| Step-back prompting | 问题复杂、需要抽象 | 先抽象原则，再解决具体问题 | 可能变得太理论。 |
| Chain decomposition | 多步骤任务 | 拆成理解、分析、生成、检查 | 步骤太多会增加成本。 |
| ReAct | 需要工具、搜索、验证 | 让模型交替推理和行动 | 需要真实工具配合，否则容易假装验证。 |
| Self-critique | 需要提高质量 | 生成后按标准自查 | 自评可能宽松，最好配外部测试。 |
| Schema output | 需要程序消费 | 明确 JSON/schema/table 字段 | 模型可能输出非法 JSON，需校验。 |
| Eval flywheel | 生产级提示词 | 用样例集、评分维度、失败案例持续迭代 | 前期建设成本较高。 |

## 高质量提示词骨架

```markdown
你是{{角色}}，目标是{{任务目标}}。

背景：
{{上下文}}

输入：
{{输入内容}}

请按以下步骤处理：
1. {{步骤一}}
2. {{步骤二}}
3. {{步骤三}}

输出格式：
{{表格/JSON/清单/报告结构}}

质量标准：
- {{标准一}}
- {{标准二}}
- {{标准三}}

如果信息不足，请先列出缺口；不要编造。
```

## 何时不需要复杂提示词

| 情况 | 做法 |
| --- | --- |
| 只需要一次性改写 | 给目标、风格、原文、限制即可。 |
| 只需要简单问答 | 直接问，要求引用依据或标注不确定性。 |
| 任务很熟悉 | 用短模板，保留输出格式和验收标准。 |
| 结果用于生产 | 必须加测试样例、边界案例和人工验收。 |
